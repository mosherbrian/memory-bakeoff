# Cycle62 — fewer components can carry the responsibilities

Tern ·26 September2026 · complete: all three panel syntheses read. Existing evidence only; no new source, experiment or deployment. [Commission](panel-cycle62.md), [opinion](opinions/corvid-c62.md).

**Accept the rival:** retained evidence, accessible observation and an executive using existing retrieval/context facilities can be a sufficient starting arrangement. A separately maintained write-time projection is optional where read-time interpretation is adequate. This agrees with the memo's responsibility-versus-service distinction; it makes the minimal alternative more concrete.

**What moves rather than disappears:** choosing active guidance, resolving supersession and retiring invalid recommendations still happen, now principally at use time. Fresh observation establishes accessible environmental facts; it does not reconstruct commitments, pending actions or the sponsor's intent. Those forms of task state still need representation somewhere. Likewise, calling retrieval and composition executive acts does not eliminate their access tools, context budget or host instruction precedence. The three-part description is a deployment hypothesis, not measured coverage of all five responsibilities.

**Bound the integration trigger:** many hosts or a large history justify investigating delivery or retrieval limits, not automatically choosing an integrated runtime. Native shared files, host refresh, selective handoffs or a lightweight index may suffice. A candidate runtime must demonstrate the missing operation on the relevant hosts. Correction delivery is one plausible gap, not the only possible one; discovery, preservation, applicability and update failures remain live possibilities without a diagnosed incident.

**Interim decision:** nominate no new component by default. Retain the simpler arrangement as a credible rival, and add machinery only for a concrete operation whose benefit warrants its costs. No claim that observation replaces task state or that executive ownership alone guarantees lifecycle handling. Medium confidence; installed behavior and the practical bottleneck remain unmeasured. Other panel pieces pending review.

**Kiln:** accept the facility/convention/unknown distinction and the five-part mapping as a practical starting hypothesis. Qualify its coverage: verbatim storage covers what was captured, not necessarily every source event, branch or artifact; committed Git history covers committed content. Grep/FTS offers lexical discovery, not demonstrated semantic or causal retrieval. No evidence here establishes a 2k cap as suitable for Brian. Per-host assembly can satisfy accountable composition without a separate cross-host composer, provided actual precedence and delivery are understood. [Opinion](opinions/kiln-c62.md).

**Scheduled capture remains a candidate:** “the closeout nobody runs” and “single missing operation with no native facility” are not established observations. The prior inventory includes host hooks, background reflection and upstream adapters; installed coverage and reliability remain unknown. Where useful lessons are actually failing to reach canonical guidance, scheduling could remove a missed trigger. It does not by itself solve semantic admission, safe revision, source preservation or later delivery. Compare with existing event-triggered capture before adding another loop; no installation follows from this nomination.

**Dissent retained:** Corvid nominates no addition; Kiln nominates scheduled capture. Tern keeps scheduled capture on watch for a diagnosed trigger gap, with no default component added and no claim that the rest of the arrangement is already verified on Brian's hosts. Reader synthesis pending.


**Cairn:** accept the warning against inferring component boundaries from responsibilities or bundled results. Correct the claimed discriminators: the c33 LongMemEval read establishes a successful recipe without write-time supersession, not a matched victory over supersession pipelines or an implementation on Brian's native stack. ReMe's utility counters support a retirement rule within a larger acquisition/retrieval/evaluation loop. They do not bound prompt tokens, total retained entries or working memory, and their utility attribution/supervision limitations remain. A footer is a possible representation of counters, not the tested whole mechanism. Cradle's module ablations constrain some bundle-level explanations even though they do not price component decomposition. [Reading](reading/c62-architecture-decision.md).

**No proof by subtraction:** lack of a decisive separate-component comparison does not establish that files plus judgment fulfill all five responsibilities. Existing logs must actually capture what recovery needs; lexical search may miss semantically related evidence; the host participates in composition and precedence. Do not add utility footers as a universal convention. Nor require repeated measured failures before any useful component can be considered: a clear unmet requirement or credible prospective benefit may suffice, with rigor proportionate to consequences.

**Final architecture decision:** no new component selected. Keep the roadmap's responsibilities, map them to existing facilities where coverage is credible, and retain explicit unknowns where it is not. Corvid proposes the three-part arrangement; Kiln nominates scheduled capture; Cairn favors native handling with conditional current views. Tern keeps capture automation on watch for a concrete trigger gap and rejects a universal counter scheme. This is a medium-confidence practical starting point, not a demonstrated five-layer implementation. Next read one focused primary study on context placement to examine the bounded-working-memory/composition boundary directly.
