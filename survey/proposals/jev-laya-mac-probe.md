# Proposed Mac probe: can local Laya reduce irrelevant memory delivery?

Tern ·26 September2026 · **larger initial draft, superseded for the first run by the bounded 46-case design in [cycle67](../panel-cycle67.md)**. Brian now authorizes one small LAN probe after fair panel design; this 240-pair relevance proposal remains deferred and unexecuted.

**Recommendation:** worth asking Brian to approve a small offline diagnostic after the panel reviews it, provided usable labels can be assembled from existing evidence. Start with **task–record relevance screening**, not destructive storage/retirement or a general clarity judge. The installed Mac path makes this a concrete candidate; its exact checkpoint and performance still need measurement. If building credible labels requires substantial new work from Brian, defer rather than treating his attention as free. No approval is requested by this document.

**Question:** for a fixed candidate set, does Laya reduce irrelevant delivered records without losing required evidence, beyond a simple lexical-plus-scope rule? A positive result supports this operation only—not “cheap classifiers solve memory,” safe deletion, or useful downstream actions.

1. **Freeze a small, inspectable dataset before calls.** Proposed scale: 240 task–record pairs from existing procedure/preference scenarios, grouped by originating task/episode; 80 for rubric/calibration, 160 held out. Preserve all pairs from the same episode in one split. Include required evidence, topical distractors, wrong-project near matches, old-but-needed history, explicit corrections, quoted/hypothetical material and insufficient context. Each label needs a source-backed reason tied to the task; independent review resolves disagreements or marks ambiguous, without seeing classifier scores. Do not label silence as satisfaction or use a generative judge's answer as gold. Counts are a proposed effort bound, not a statistical power claim.
2. **Keep the deployment prior honest.** Use a representative slice if available, and report deliberately enriched hard cases separately. If only constructed fixtures exist, say so; do not infer a real false-exclusion rate or service-wide savings. The old pi-lcm 22/33 finding is retrieval displacement, not a directly comparable pairwise relevance or supersession score.
3. **Record what runs, after approval.** Mac model/checkpoint hash or release, package/runtime, device, input limits, truncation, question text, option mapping and existing temperature settings. No install/update, service reconfiguration, hook or production memory writes in the proposed run. Missing identity should stop interpretation, not trigger unapproved repairs. Run local Laya only; Jev API use or egress would require a separately scoped comparison.
4. **Compare matched inputs and budgets.** Baselines: keep all; majority/input-blind prediction; deterministic scope plus lexical ranking. Candidate: one fixed binary relevance question (with an uncertain/defer policy), using the installed checkpoint. Preserve raw outputs. Report untuned performance; if temperature/threshold fitting is justified, use only the calibration split and freeze it before held-out scoring. Do not reuse published ECE or a Jev confidence threshold. A positive scalar temperature can change probabilities without repairing wrong ranking or classification.
5. **Check question sensitivity without tuning on the test.** Predeclare a small diagnostic subset for option-order/name permutations and a meaning-preserving wording change, keeping the rubric constant. Inspect the actual `noul` versus Choice field semantics; do not assume interchangeable thresholds or complementary probabilities. These diagnostic variants must not select the best test-set prompt after the fact.
6. **Score the policy, not just the model.** Report the confusion matrix; required-evidence recall; harmful exclusions by hard-case category; risk versus retained/deferred coverage; calibration/Brier score with bin/sample limits; and saved records/tokens. Measure Mac end-to-end cold and warm latency, batch throughput, input preparation and fallback cost. Keep “saved context” distinct from faster total work. Include label/preparation effort in the ledger. Use counts and uncertainty intervals; one small clean result cannot certify a rare-error bound.

**Decision rule to settle before approval:** compare exclusion policies at matched required-evidence recall and show their error/work-saved tradeoff. If Laya provides no useful improvement over the deterministic rule, or high-confidence mistakes discard corrections/dependencies, reject this gate. A useful result warrants only a follow-on reversible shadow deployment proposal; production adoption would still need action-level evidence. Do not pick a threshold on the final holdout or silently turn this probe into fine-tuning.

**Why not supersession first?** A narrow contradiction classifier is worth a later design, but wrong retirement changes future evidence. A relevance diagnostic tests whether this installed model discriminates useful memory at all while leaving the source and active store unchanged. The panel may argue for a better first binary decision; that disagreement is part of cycle67.
