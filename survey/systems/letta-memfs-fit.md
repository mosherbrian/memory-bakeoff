**Budget boundary matters.** [memory-constraints.ts](https://github.com/letta-ai/letta-code/blob/main/src/memory-constraints.ts) defaults are depth2, 20,000 characters/file and 65,536 core characters. Core aggregation here applies to root-level files in the `root-marker` layout; skills are excluded from memory-file checks. Per-pattern overrides can remove a file limit. These are Unicode character counts, not host token/byte/line caps. Configured checks can reject oversized memory within their contract; `/doctor` flagging alone does not prevent truncation. Consequently “directly prevents Brian's MEMORY.md failure” needs the active layout, trusted policy, validation path and recipient load limit to align. No blanket guarantee for other hosts.

**Current source versus earlier docs:** [harness prompt](https://github.com/letta-ai/letta-code/blob/main/src/agent/prompts/letta_local_memfs.md) distinguishes the current compiled prompt from later memory revisions, and gives the harness sync/refresh responsibility. [Reflection settings](https://github.com/letta-ai/letta-code/blob/main/src/reflection-settings.ts) establish configuration types, not successful background execution. [Dreaming docs](https://docs.letta.com/configuration/memory) supply the trigger/worker description. All are vendor mechanism evidence, not outcome measurement.

**A read-only Claude/Pi view is feasible as a file-consumption design, not turnkey shared MemFS.** The [repository-sync mechanism](https://github.com/letta-ai/letta-code/blob/main/src/skills/builtin/syncing-memory-filesystem/SKILL.md) supports an additional Git mirror: main-branch commits initiate background pushes; failures do not block commits and have a status log. It is not synchronous delivery. It also documents root-index versus legacy layouts. Proposed shape: Letta is sole writer; a separate checkout is exposed read-only through filesystem/host permissions; existing host instructions point to a small scoped entry view, with detail read on demand. Pin/report the delivered commit and refresh through an existing Git/deployment path. A Git hook is not a read-only filesystem boundary. Import neither the whole agent persona nor an unbounded tree. Recipient load/reload limits still apply. This is a design inference; no adapter was implemented or tested.

That mirror does **not** include recall messages by implication, ingest Claude/Pi sessions, run reflection outside Letta, enforce consumer actions, or guarantee readers see the newest commit. Without a supported input path for their transcripts, Letta cannot maintain lessons from those hosts automatically. If recurring glue is needed, prefer testing the whole Letta runtime over building a new mirror pipeline first.
