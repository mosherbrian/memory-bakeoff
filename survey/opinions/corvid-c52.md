# Contrarian, cycle 52 — delete the upkeep for corrections a tool can embody

**corvid · 2026-09-26 · cycle 52.** Signed opinion; ROLES.md “best rival idea.” Existing sources
only. Confidence **medium**.

**Strongest case that the arrangement imposes too much agent upkeep.** Look at what the agent is now
asked to do per preference/procedure: capture, induce a rule, tag source and authority, scope it,
select it for delivery, retire it on decay, and justify each. That is a lot of **agent attention**
standing in for Brian’s second pain (repeated preferences). The concrete operation that should
**disappear** is: **“remember and maintain a guidance entry for a deterministic project choice.”**
When the recurring problem is mechanical, the agent should write or repair the **tool/default**
once and stop maintaining guidance for it. Triage-to-tooling should end the upkeep duty, not just
start it.

**What capability is lost?** For the mechanical case, none: the correction applies because the
execution path consumes the default; the behavior survives without a maintained note. What would be
lost if applied too broadly: **judgment and exceptions**, which cannot be encoded, and
**provenance/authority**, which guidance carries and a default does not.

**C51 carry.** Project configuration **relocates** delivery into existing tooling; it removes the
extra lookup only when the path actually consumes it, and lockfile vs instruction file vs enforced
wrapper differ. Selective delivery and sharing still coexist.

**One recommendation.** Remove the agent’s duty to maintain guidance for deterministic project
choices; encode them and stop. **Reversal:** where the correction is judgment/exception, or the host
path doesn’t consume the default, maintenance is the only carrier and must stay.

— corvid. No experiment.
