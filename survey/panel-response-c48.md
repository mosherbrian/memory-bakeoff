# Cycle48 — outcome relevance before route conformity

Tern ·26 September2026 · **complete synthesis: all three panel pieces read**. [Independent methods](reading/tern-c48-action-endpoints.md).

**Memo change:** judge a preference-bearing action by the useful result as well as obeying actual constraints. Selecting the expected function is diagnostic; it is not automatically the user's objective. A permitted alternative route may be equally useful. This extends the existing recall-versus-use distinction without a new logging requirement.

**Corvid:** accept behavioral evidence and the action endpoint as useful additions. Correct synthetic histories to real Amazon behavior records plus generated profiles/instructions. Table5 actually ablates memory,SFT,DPO; coupling alone cannot establish lack of component evidence. Its boundaries still matter, including whether removing memory changes training. A stated preference does not make behavioral context useless, and inability to cheaply check an action does not establish that a profile alone suffices. Existing history can supply the evidence; no new store or training run follows. [Opinion](opinions/corvid-c48.md).

**Kiln:** accept function-conditioned selection of fields as a candidate. It follows cosine top-K, not a replacement for top-K retrieval. Reject function accuracy as the first success criterion: AppendixA.4.5 explicitly introduces outcomes independent of search/recommendation route, while Table5 function accuracy stays .994 across variants with very different result scores. “No correction loop anywhere” is too broad: simulated users give feedback, and InteRecAgent updates profiles after tasks. Durable current-preference semantics and actual human correction cost are separate unresolved matters. Full PUMA is not tested multi-turn (§6.1.2), so do not transfer its single-turn results to that track. [Card](systems/personalwab.md), [opinion](opinions/kiln-c48.md).

**Cairn:** accept real behavior versus generated profiles, temporal holdout within recurring users, and the executed-function endpoint. Table5 is a component ablation, not an unchanged-policy experiment: removing SFT or DPO changes the executor's training; the memory removal protocol is not fully specified. Heuristic labels initialize SFT; DPO uses best/worst sampled parameters scored by results. Near-no-memory overall scores are a single-turn observation, not every task or the multi-turn track. Multi-turn retrieval does improve results with more steps. Table3 also contains a GPT-based PUMA row, so “only retrieval plus training moves it” is too categorical. Training hardware is reported; a full cost ledger is absent. A 7B model's reported timing versus GPT calls is not a Strix Halo deployment comparison. Outcome proxies do not establish user satisfaction. [Reader](reading/c48-personalwab.md).

**Remaining limits:** profile-generation temporal scope remains uncertain, not a demonstrated leakage finding. Table headings say GPT-4o while implementation text names GPT-4o-mini; preserve that source discrepancy rather than silently choosing an identity for cost claims. Full trained PUMA is not evaluated multi-turn. No real-user correction-burden result follows.

**Decision:** prefer relevant task outcomes over route conformity while respecting actual constraints. Historical behavior can help, but neither more history nor a technically valid call guarantees better personalization. Medium confidence in this advice; no new store, mandatory metric, training run or product selection.
