# Source recovery and useful retrieval

**Tern · 26 September2026 · primary reading, no run.**

**Hindsight correction.** [Documents API](https://hindsight.vectorize.io/developer/api/documents) provides original document content, retained text chunks and same-ID updates that replace old content/facts. Thus retention is real but not an unconditional append-only archive. [Recall API](https://hindsight.vectorize.io/developer/api/recall) can include raw chunks, document/chunk references and observation source facts. These optional, budgeted responses mean a separate document-fetch tool is not the only route to source text; truncation is explicitly signaled. This closes more of the API provenance gap than Kiln's initial card found. Exact Pi adapter exposure remains the narrower open question. Medium confidence in documented behavior, no local verification.

**HippoRAG2.** [Paper v1, §§3–6, Appendix F](https://arxiv.org/html/2502.14802v1) adds passage nodes to a phrase graph, uses query-to-triple matching and LLM filtering, then ranks passages through Personalized PageRank. The reader consumes retrieved passages rather than relying solely on generated summaries. Comparisons use a common QA reader and report retrieval separately; prompt optimization and indexing/filtering calls are part of the method. Reported improvements support discovery across the tested QA tasks, not correction of changing preferences. The under-$2 indexing example uses a particular batch API/corpus; it is not a complete upkeep cost. Static QA is not a longitudinal procedure trial. Keeping source passages does not make applicability judgments cheap or automatic. **Medium confidence in transfer:** useful source-directed indexing can sit beside lifecycle logic without becoming another truth store.
