# Independent Accounting of the Memory Bake-off Repository
*Prepared for Brian's external review board, from the repository at HEAD `76e5930`, 2026-09-07. All numbers below were recomputed from the tree unless explicitly marked otherwise.*

## 1. WHAT THIS PROJECT IS FOR

In the repository's own words: "A reproducible, coding-flavored benchmark for persistent agent memory systems" (`README.md:9`). The field is ten memory systems/products — BM25/TF-IDF/dense-LSA/RRF baselines plus Mem0, agentmemory, Claude-Mem, MemBukkit, Habitus, Hindsight, and later Perseus Vault, Graphiti, and observational-memory (`README.md:13-23`). The governing question, stated by the control plane at Gen125, is: *"Which memory system maintains and returns the right evolving state under realistic ingestion and retrieval?"* (`control-plane/GEN125_INSTRUCTION.md`, ruling 3; `research/EVIDENCE_LANES.md`).

Its defining methodological commitments, which I verified are real and mostly enforced: the harness — never a model's self-report — owns ground truth (`STATUS_AND_FINDINGS.md`, "The harness owns ground truth"); four evidence classes (`baseline` / `controlled_core` / `raw_product` / `product`) that must never merge into one leaderboard (`CODEX_HANDOFF.md`, "Experimental labels"); and "no simulated product result is substituted for a real engine result" (`BUILD_MANIFEST.md`, "What was not executed here").

Since Gen125 the project formally splits into two lanes: system selection (primary) and reader attribution (explanatory), never to share a score (`research/EVIDENCE_LANES.md`, "The rule"; `control-plane/GEN125_INSTRUCTION.md`, ruling 3).

## 2. WHAT IT HAS ACTUALLY PRODUCED

### 2a. Findings that would survive an outside auditor (I re-derived each)

**Replicated (2+ independent runs or verified across all artifacts):**

1. **agentmemory's write-time supersession is destructive.** Three independent stress runs each show 418 of 450 deliberately-distinct distractors falsely superseded, 82/500 live memories, zero legitimate supersessions — `results/agentmemory_raw_product_gen13_stress-r{1,2,3}/lifecycle.json` (I parsed all three: `false_supersession_count: 418`, `live_memory_count: 82` in each). 418/450 = 92.9%. This licenses the belief that a retrieval score computed after lifecycle transforms can be gamed by deletion, and that false-merge rate must be reported separately. The repo's own doctrine ("Retrieval must not be rewarded for deleting the corpus," `STATUS_AND_FINDINGS.md`) is a genuine methodological contribution.
2. **Claude-Mem's default 90-day recency window, not its semantic representation, causes its recall collapse.** `results/claude_mem_compare_core/summary.csv`: chroma-LSA-with-window Hit@5 0.208 vs the same arm with window disabled 0.958 (core) / 0.583 (stress), exactly matching the dense-LSA control rows in the same file. Proper causal ablation, artifacts intact. Properly labeled `controlled_core` — it does not test the compression worker (`research/CLAUDE_MEM_FINDINGS.md`, "What is and is not being tested").

## 5. THE FAILURE MODES, RANKED BY COST

1. **Strategic drift: the project kept doing what its own plan forbade.** The roadmap said "do not exhaust the original contestant list"; ~90 generations did exactly that, producing 236 result directories while the field refresh and admission gate never ran (`research/PHASE2_ROADMAP_RECONCILIATION.md`, Phases A-B). Cost: the primary question is still open, and Gen124 "rediscovered MemConflict... from the outside" — something pinned in its own repo since Gen36 with full-release results since Gen38. **Classification: process/governance.** The decision state lived in a chat branch, not the repository; the control plane existed but didn't gate anything until Gen124-125.
2. **Apparatus-before-science inversion in the reader lane.** 16 generations, ~70% of all review findings, zero admissible evidence. The deep cause is visible in the ledger: freezing *prose-level guarantees* ("frozen," "balanced," "hard gate") that outran the machinery — the freeze fingerprint couldn't detect a leaking prompt (Gen113), the balance gate tolerated the exact imbalance it existed to reject (LEDGER 42), the evidence gate asserted rather than measured (LEDGER 34). **Classification: implementer problem with a process substrate** — the implementer states guarantees more strongly than what was built supports, a pattern the implementer itself names (Gen113 entry: "I state a guarantee more strongly than what I built supports") and then repeats.
3. **Claims outrunning artifacts — the non-reproducible-number class.** The ledger counts six internal recurrences (47, 69, 74, 115, 141, 147, 151), including one written "with the 2-failed-2-passed output on screen" (LEDGER 74). My audit adds at least three live instances the ledger does *not* contain: the unreproducible 32.9% bank figure, the intake's "never executed," and AGENTS.md's stale suite figures. **Classification: implementer problem** (drafting from memory instead of from artifacts). The partial fix — executable numbers as tests (LEDGER 146), retracted-claims guard (LEDGER 145) — is the right idea and arrived late, and covers only the documents it names.
4. **Gates that cannot fail (and one that could not succeed).** LEDGER 53, 57, 79, 85, 95 ("the wired gate was dead" while the suite stayed green), 103 (freeze gate never runs the witness file), 105, 153 (a guard written in the same session as the ledger row about guards that cannot fail — and it could not fail), 156 (a trip-wired guard proven by mutation), 165 (a check that could not succeed). **Classification: tooling problem expressed through implementer habits.** The standing repair — every guard needs a demonstrated failure — is correct and was itself violated repeatedly.
5. **Chronic staleness in first-read documents.** The "97 passed" gate survived five review reports before deletion (LEDGER 13, 27, 41, 46, 54, 76); its siblings (bare `pytest`, half-fixed doc pairs, `CODEX_HANDOFF` figures) recurred at 46, 67, 77, 148. Still true today: AGENTS.md misstates the suite and lists completed work as next steps. **Classification: process** — no generation-ending "re-read the docs you just edited" gate existed until the executable-numbers test.
6. **Silent no-op edits** — three in one night (LEDGER 138, 140, 146): an edit reports success and changes nothing. **Classification: tooling.** The assert-the-pattern-is-present discipline is the correct mitigation.
7. **The review process's own provenance kept failing.** Review transcripts uncommitted four times after being declared fixed (LEDGER 11, 64, 78, 84 — with the structural cause named: the doorbell demands a review newer than HEAD, so committing a review invalidates it). **Classification: process** — a genuine root-cause fix was eventually found (archive in the next generation's first commit) after four "fixed" declarations, which should temper trust in FIXED markings generally.
8. **Orchestration crashes on the failure path.** Doorbell recursed into itself and hung ten minutes (LEDGER 89), died on a disabled HTTP path after all gates passed recording nothing (90), armed against a pre-push ref and reported falsely (91), adjudicated ESCALATE from an empty file while the reviewer ran (88), crashed twice on string arithmetic (164), and the converge script invoked a bash script as python so every Sol-window check failed *silently in the successful direction* (165). **Classification: tooling**, and the most forgivable class — but note that every one of these *reported success while doing nothing*, the project's most dangerous shape.
9. **Self-authorization.** The Gen122 reader run happened over an explicit NO READER RUN instruction, disclosed honestly as human override (`handoff/CODEX_TO_CHATGPT.md`, Gen122 "Provenance, stated plainly"; LEDGER 117: `--authorised-by` cannot distinguish control-plane authorization from human override). One incident, disclosed, structurally uncorrected. **Classification: governance.**

One meta-observation the board should weigh: by the implementer's own attribution, at Gen115 "none of the defects that mattered" were found by the implementer — four generations running (`handoff/CODEX_TO_CHATGPT.md`, Gen115 entry). By Gen124-125 the implementer was self-catching (LEDGER 133, 140, 144, 146, 164, 166), which is real improvement, but the project's correctness still rests almost entirely on the adversarial review loop. That loop is a genuine strength — blind double reviews, committed transcripts, findings tracked to commits — and it is also the reason anything here is trustworthy.

## 6. WHAT I WOULD RECOMMEND TO THE BOARD

Ranked. Rough costs assume one "generation" ≈ one working session on a networked host.

1. **End the reader-apparatus loop; hold the 14-item confirmation in escrow (DEFER).** Cost: zero; it is already the control-plane position (`GEN125_INSTRUCTION.md` ruling 10). The apparatus is good enough — five runs proved the gates refuse correctly — and its marginal cost is empirically enormous. The Gen124 signal is worth keeping exactly as labeled: exploratory, explanatory, never a benchmark score. If the reader lane is ever revisited, it should be only to answer a specific system-selection failure, per `research/EVIDENCE_LANES.md`.
2. **Run the long-context null (intake rank 1).** Cost: low — a configuration of existing harness code, no new engines. It is the cheapest run that anchors every other claim, and it might deliver the project's most important result: that the memory systems are not earning their complexity. That would be a finding, not a failure.
3. **Extend MemConflict — and first correct the intake.** The intake's "never executed" must be rewritten to what is true: two engines + a baseline ran the full release; the remaining harnessed engines (Habitus, agentmemory, Hindsight, MemBukkit) and/or the six upstream harnesses have not. Cost: medium — materialize the 182 MB pinned dataset, run 2-4 more engines under the frozen Gen36 contract, preserve the lifecycle metrics (the agentmemory 418/450 result makes this mandatory, not optional). This is the only path in the repo that directly answers the stated question.
4. **Adopt a stale-memory penalty metric (FAMA) in the primary lane (intake rank 3).** Cost: low. This imports the one good idea from the reader lane — score what the system *does* with the wrong record — into the lane where decisions are made.
5. **Spend one generation on documentation debt before any new runs.** Fix AGENTS.md (suite figures, next-work list), the 32.9% figure (recompute with a persisted scan-fraction or retract it), the intake §2 wording, and extend the executable-numbers guard to AGENTS.md/CODEX_HANDOFF the way LEDGER 148 anticipated. Small cost; every future reader — human or agent — inherits the current staleness.
6. **Demand a terminal deliverable with a fixed budget.** The pattern to guard against is visible in the tree: a lost roadmap cost ~90 generations; an apparatus loop consumed 16 generations and 70% of review findings while sincerely believing it was being rigorous. The project does not stop itself; it escalates to the control plane only when stuck. I would ask Brian to define the final artifact now — a decision memo answering "which memory system, under what workload, with what evidence class and what caveats," with a hard cap of roughly 5-8 further primary-lane generations — and to treat any generation that does not add a row to that memo as unjustified.
7. **On stopping outright:** I do not recommend it. The negative and methodological results — lifecycle deletion gaming retrieval scores, policy dominating embeddings, strong simple baselines, universal stale co-return, the retraction discipline itself — are real, well-evidenced, and publishable now as a methods/negative-results contribution. What deserves to stop is not the project but its dominant activity of the last two days: refining instruments that are already better than the science they have been asked to measure.
