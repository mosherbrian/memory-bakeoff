VERDICT: DEFECTS_MINOR

**Most important finding:** the capture invariant itself is genuinely enforced — but any run containing at least one non-COMPLETED response alongside a completed one crashes at `scripts/run_reader_v6.py:553` (`served_models: sorted({r["served_model"] for r in responses})` mixes `None` with strings → `TypeError`, reproduced) *after* closure but *before* the marker is written, so the graceful NON_EVIDENCE pathway built in rounds 4–7 never executes for exactly the partial-failure runs it was built for, and the attempt is left markerless — recoverable only by editing a contract-bound runner, which per this repo's own rules forces a refreeze.

The core lifecycle question checks out: the transport `try` (lines 318–322) cannot practically catch anything beyond obtaining the bytes; receipt → `EV.journal_append` with `os.fsync` (`evidence.py:123-142`) → decode/parse as terminal dispositions with bytes kept; every post-capture exit is a `return`, so no journalled response can ever be retried, replaced, or reinterpreted; `write_raw`/`write_evidence` refuse overwrites; the seal is computed from disk; `verify_closed` is observed, not asserted; the marker is written last.

Other defects, most severe first:

1. **Zero-capture runs crash instead of sealing NON_EVIDENCE** (`run_reader_v6.py:506`). If all 60 cases exhaust transport retries, `journal_append` was never called, the journal file does not exist, and `EV.manifest_existing(out, JOURNAL)` raises `FileNotFoundError` — same family as the headline finding: partial/failed runs never reach their derived marker. (Fail-closed, no data lost — no bytes ever existed.)
2. **`refuse_to_resume_an_exposed_run` is unreachable as wired** (`run_reader_v6.py:487-488`). It is called on `out` returned by `EV.next_attempt`, which by construction does not exist — so its journal cannot exist, and the guard can never fire except in a concurrent-process race. The documented "the run then REFUSES to resume" invariant is actually enforced by fresh-attempt-numbering plus `--authorised-by` gating, not by this gate; the witness (`test_an_interrupted_exposed_run_refuses_to_resume`) tests the function directly with a hand-made journal, so the suite is green while the wired gate is dead — the exact "check that cannot fail reads exactly like a check that passes" pattern this repo keeps finding in itself.
3. **The "transport try contains exactly one thing" invariant is prose, not structure.** The block holds three statements: `r.read()`, `status = r.status` (line 321), and the `with`-block's `__exit__`/`close()`. Neither can practically raise (`r.status` is a plain attribute; closing a fully-read `HTTPResponse` does not raise), so the handler still only catches byte acquisition in practice — but a `with`-exit failure would theoretically discard *already-received* bytes and retry, i.e. replace a received response. Behaviorally witnessed for decode/parse (the non-UTF-8 witness would fail if decode moved into the try), not for these two.
4. **No gate reconciles the graded view against the raw evidence.** Grading consumes the in-memory `responses` re-serialised into `reader_records.jsonl`; the manifest binds both files' bytes but nothing ever compares `reader_records.jsonl`'s per-case `response_sha256` against the journal's. A desync between "what was captured" and "what was graded" (bug class, not tamper) would pass every gate including closure and the three-way seal check.
5. **Durability nit:** `journal_append` fsyncs the file but never fsyncs the parent directory after creating the journal, so on power loss the freshly created file's directory entry may be lost even though its appended bytes were flushed to the platter (largely benign on ext4 data=ordered; the repo's own "fsync is the whole point" standard invites this scrutiny).

None of these touch the published result: attempt17 is a zero-call freeze, its eight artifacts verify, the focused gate is green (58 passed), and every defect above lives in post-capture failure paths that fail closed rather than corrupt or resample an already-received response.
